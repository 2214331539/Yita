# Yita 跨平台产品开发路线图

更新日期：2026-10-02。状态：计划已制定；以下未完成阶段尚未实施。当前代码事实见 [技术架构](ARCHITECTURE.md)，已完成的 Windows 验收见 [验收记录](WINDOWS_AVALONIA_ACCEPTANCE.md)。

## 产品目标与边界

交付一个可以直接安装、后台常驻、在 Windows 与 macOS 常用文本应用中划词翻译的本地客户端。默认使用用户配置的 DeepSeek 在线流式服务；“本地客户端”不表示默认离线翻译，也不表示设置、凭据与记录会自动跨设备同步。

核心流程为：拖选文本 -> 读取选区 -> 在附近显示浮窗 -> 增量显示译文。读取失败时保留“手动复制后翻译”的入口；失败、取消与权限不足不能导致程序退出或破坏正常复制。

- 首要支持 Windows x64、macOS Apple Silicon；macOS Intel 单独构建和验收后列入正式支持。Windows ARM64 与 Linux 不属于本轮交付范围。
- 保持现有设置、阅读浮窗、解释/问答、术语、修正、AI 记录、语言切换与 Yita 品牌风格。Mac 使用系统可用字体和原生菜单规则，保持相同信息结构与功能，不要求两种系统逐像素一致。
- 优先覆盖网页、Markdown、代码编辑器、Office 和可复制 PDF。拖选自动触发为主要入口；双击选词、键盘扩选在完成主链路后补充。
- 不加入 OCR、截图翻译、账号系统或云端同步，不为本轮重新更换语言或 UI 框架。
- 不承诺所有可见或可选文字都能读取。密码框、禁止复制内容、远程桌面、受保护或不暴露选区的控件存在系统边界；界面必须能解释限制并提供适当回退。

## 分支与交付方式

- `main` 为当前 Avalonia 主线。代码变更从最新 `main` 创建 `codex/` 功能分支，通过 Pull Request 合入；文档状态随交付更新。
- `codex/csharp-wpf-legacy` 和 `codex/csharp-wpf-upstream-baseline` 保留为历史基准，不用于新产品日常开发。
- 已按维护者要求删除远程 `codex/cross-platform-migration`，以及本地 `codex/windows-avalonia-parity`、`codex/yita-branding`；删除前已确认三者提交均包含在 `main` 中。
- 本地 `codex/cross-platform-migration` 按本次仅删除其远程分支的范围保留，不作为下一阶段开发入口。
- 不重写既有提交、标签或 Release。新架构使用新版本；试用版先标记 Pre-release，完成安装验收后再升级发布状态。
- 不再以分支名区分是否运行 CI。后续 CI 支持 `main`、新功能分支与 PR，并移除已删除分支的触发配置。

## 交付顺序

| 阶段 | 交付结果 | 建议功能分支 | 进入条件 |
| --- | --- | --- | --- |
| A | 可直接分发的 Windows Avalonia 试用安装包 | `codex/windows-avalonia-release` | 当前 Windows 验收基线 |
| B | Desktop 可接入两种系统的原生宿主与存储 | `codex/platform-host-services` | A 的 Windows 安装链路可重复验证 |
| C | macOS 可授权、划词和阅读的完整链路 | `codex/macos-native-selection` | B 的契约完成；Mac 构建和真实验收环境可用 |
| D | 双端兼容性与阅读体验达到试用标准 | `codex/cross-platform-polish` | C 已在交互式 Mac 环境实际运行 |
| E | 双端安装、版本检查、升级及正式 Release | `codex/cross-platform-distribution` | D 的核心场景通过，签名与分发条件就绪 |

这是实施顺序，不是固定日期承诺。Mac 环境和签名条件未满足时，可继续 Windows 分发、共享接口及协议测试，但不能宣称 Mac 原生功能已完成。

## 阶段 A：Windows 安装与发布基线

### A1. 构建工具链与版本

- 将新架构项目、相关测试、UIA helper、SDK 固定规则与 CI 在独立提交中升级至 .NET 10 LTS，验证 Avalonia、Skia 和原生依赖兼容性。界面包仅因实际兼容问题才升级，升级后检查截图与阅读行为。
- 旧 WPF 工程保留原构建目标与独立回归任务，按需在 CI 同时安装相应 SDK，避免用新工具链改写旧版技术基准。
- .NET 8 官方支持截止为 2026-11-10；.NET 10 LTS 截止为 2028-11-14。正式长期分发不能继续以临近停止支持的 .NET 8 为唯一基线。来源：[Microsoft 支持政策](https://dotnet.microsoft.com/platform/support/policy/dotnet-core)。
- 统一 Desktop、Core、helper、安装包、关于页与 Release 的产品版本，不让不同项目的版本字段决定不同下载名称。

### A2. 自包含安装包

- 为 Avalonia 新增明确的发布/Setup 入口，保留旧 WPF 脚本。发布主程序和 Windows UIA helper 各自需要的运行时、原生库与配置，并验证 helper 使用实际发布文件启动。
- 使用现有 Inno Setup 与 Yita 向导素材；普通用户安装不依赖预装 .NET 或 SDK，也不默认请求管理员权限。
- 将根 MIT、上游完整许可、字体、Avalonia/Skia、Microsoft 运行时及其他实际分发依赖的声明纳入包清单；缺失时构建失败。
- 明确新旧安装版的应用身份、启动项和目录策略。升级前退出旧进程、释放钩子和快捷键；旧偏好导入须可取消，不覆盖用户的新配置。
- 安装版与开发预览的启动脚本和身份需要明确，避免开发者不知运行的是哪个 EXE。默认验收只运行一份拥有全局输入的实例。

### A3. 验收与交付

- 在未安装 .NET 的干净 Windows 10/11 x64 环境验证安装、首次配置、真实翻译、后台启动、二次启动、升级和卸载。
- 检查 WPS PDF、普通网页、VS Code/Markdown、普通复制，以及 helper 缺失或异常后的失败处理。
- 升级保留设置、Key 和用户记录；卸载移除程序、启动项和输入捕获，不默认删除用户数据。
- 交付自包含目录、Setup、SHA256、许可清单、安装测试记录和可回退的 Windows Pre-release。证书可用时签名；未签名试用包需准确说明状态。

## 阶段 B：平台宿主与存储

- 把 `App`、`MainWindow` 和托盘当前直接依赖 `WindowsSelectionRuntime` 的入口收拢到平台服务边界，包括选区事件、剪贴板翻译、外部点击、启用/暂停和释放资源。
- 继续复用现有 Windows runtime，只迁移接入点，避免同时改写已验收的 UIA 与复制策略。新增抽象只覆盖 Mac 接入所需的实际功能。
- 平台服务按系统创建：单实例/唤醒、原生取词、状态菜单、启动项、权限状态、凭据和修正数据保护。Core 不直接调用 Windows 或 Cocoa API。
- 保持两种平台使用相同的 `SelectionRequest/Result`、取消和错误模型；为 helper 超时、崩溃、重启、重复事件和退出建立共享协议测试。
- Mac Keychain 实现需实际复验，必要时改用原生 SecItem API；API Key 不进入命令行、普通设置或诊断日志。
- Mac 修正数据采用系统凭据保护的密钥和经过验证的加密实现；加密失败时不能无提示降级为明文。普通内存缓存与可选 Markdown AI 记录沿用当前语义。
- 设置增加 schema 版本和迁移测试，保存保持原子性；不同平台的数据目录、启动项和支持状态明确。双端使用不等于将 Windows DPAPI 文件复制到 Mac 后即可解密。

验收：Windows 原有链路和 UI 回归通过；Desktop 可用可控的原生事件驱动同一浮窗；不支持的服务返回可读状态，而非假装成功。

## 阶段 C：macOS 原生链路

### C1. helper、权限与输入

- 使用 Swift/Cocoa helper 承载 AX、全局输入和菜单栏；C# 保持业务和 Avalonia UI。helper 在自己的 Cocoa 主循环运行，不把跨进程阻塞放在 UI 回调内。
- 使用结构化 IPC、请求编号、协议版本、超时与响应长度约束。区分权限拒绝、无选区、目标消失和 helper 故障；限制 helper 重启频率，防止重启循环。
- 先固定 `.app` 的 Bundle ID、helper 身份和开发签名策略，再实施 Accessibility 授权，避免测试二进制和正式包被系统视为不同应用。
- 根据实际使用的事件 API检测 Accessibility/Input Monitoring 能力，只引导用户授予所需权限。覆盖首次拒绝、之后开启、运行时撤销和系统设置跳转。
- 捕获拖选结束和全局快捷键，保留来源 PID、触发坐标和前台目标；原生回调只入队。注入的复制事件与 Yita 自己的窗口不得再次触发翻译。

### C2. AX 优先与 Cmd+C 回退

- 从前台/命中应用读取 `AXSelectedText`，必要时根据 `AXSelectedTextRange` 获取文本；使用 `AXBoundsForRange` 等已支持接口查询选区边界。
- 外部 AX 调用设时限，慢速或异常目标不能阻塞后续选区；helper 故障不能使 Avalonia 退出。
- 无 AX 文本时，在仍为原前台目标且安全可复制的情况下执行 Cmd+C；以 NSPasteboard 的 `changeCount` 和格式稳定状态判断结果。
- Mac 没有与 Windows 剪贴板所有者完全相同的校验能力，不能机械复制 Windows 策略。依靠原目标校验、时间范围、序列变化及竞态测试避免取到其他应用的新复制。
- 回退前保存可完整恢复的 pasteboard items/类型；无法保存则停止自动复制。恢复只发生在序列仍属于当前事务时，用户后续复制优先。
- 密码控件、终端等危险目标不自动发送复制；用户主动复制后通过快捷键翻译仍可用。AX 不支持但 Cmd+C 正常的 PDF 必须覆盖回退验收。

### C3. 窗口与桌面生命周期

- 将 Cocoa 屏幕坐标、选区边界与 Avalonia 逻辑坐标统一，覆盖 Retina、外接屏、负坐标和不同工作区。没有可靠边界时使用此次鼠标坐标作为锚点。
- 验证浮窗出现时保留来源应用焦点，正文交互时才按需激活；固定、外部点击关闭、Esc、拖动和相对偏移遵循现有语义。
- 在 Avalonia/Cocoa 可用能力上实现 Spaces、全屏窗口、置顶与隐藏行为；只在需要时增加 NSPanel 或宿主适配，不建立第二套业务 UI。
- 使用 NSStatusItem 菜单栏入口，支持设置、暂停、手动翻译、诊断和退出。增加 Mac 单实例、重新唤醒、登录启动和退出清理。
- 使用系统中文/拉丁字体回退，检查中英文、长词、换行和尺寸测量；不得为了像素相同而未经许可分发 Windows 字体。

验收：在真实 Mac 上完成“授权 -> 外部划词 -> AX/复制回退 -> 浮窗 -> DeepSeek 流式 -> 正常复制 -> 重启”的完整流程。只有编译、Headless 测试或 Mock 翻译通过不能作为此阶段完成证据。

## 阶段 D：双端兼容性与体验

### 应用矩阵

| 平台 | 必验目标 | 重点 |
| --- | --- | --- |
| Windows | Edge/Chrome、VS Code、WPS PDF、Word/WPS 文档、Adobe Reader、常用 Markdown 编辑器 | PDF 回退、跨进程选区、普通复制、多显示器 |
| macOS | Safari/Chrome、VS Code、Preview PDF、Word、常用 Markdown 编辑器 | AX 差异、Cmd+C 回退、授权、Retina、Spaces/全屏 |

每条测试记录 OS、CPU 架构、应用版本、权限和实际读取来源。明确区分支持、有限支持、需要手动复制与不支持；不得用某款应用一次成功代表整个平台兼容。

### 主链路与体验指标

- 固定可复现文本和操作集，分别测试短词、段落、长文、快速连续划词、慢服务、断网、限流和取消；测试过程中目标应用与剪贴板均不能被意外改写。
- 支持矩阵内用每应用至少 100 次有效拖选记录成功率、失败原因及 p50/p95 取词耗时。初始目标为有效选区成功率不低于 95%；发布前根据真实结果公开支持边界。
- 直接读取的初始 p95 目标为 300ms 内、复制回退为 1.2s 内；从手势稳定后计时，与可配置防误触延迟和网络响应分开报告。目标需在真实环境测量，不能只缩短等待以增加误读。
- 浮窗先显示可反馈的状态，首段译文到达立即呈现。测试流式期间不跳位、完整显露/可滚动、手动缩放优先、相对位置、固定多窗口、中英文、键盘复制和减少动画。
- 验证短时连续至少 100 次选区与至少 2 小时交互/后台运行；无未处理崩溃、挂起、helper 泄漏或持续增长的请求。睡眠唤醒、锁屏、显示器变化和权限撤销后能够恢复或给出明确状态。
- 记录空闲/取词/流式状态的 CPU、内存和 helper 数量，先建立基线，再处理真实热点；不得为了性能削弱超时、来源校验和剪贴板恢复。
- 补充双击选词和键盘扩选，使用实际系统事件或选区通知；避免启动持续高频读取。尊重暂停开关和正在交互的 Yita 窗口。
- 诊断只记录版本、平台、方法、耗时、错误类型和权限状态；不默认记录正文、译文、完整路径或 API Key。失败提示对应实际原因，保留手动复制入口。

验收：两端常用场景达到矩阵标准，Windows 已验收功能无回退；网络问题、原生读取失败和界面错误可区分。未测的系统或应用不标记为已支持。

## 阶段 E：双端分发与更新

- Windows 输出自包含 Setup；Mac 首先输出独立 `osx-arm64` 的 `.app` 与 DMG，再加入经验证的 `osx-x64` 包，不把多个 .NET 包简单合并就宣称 Universal。
- 最低 macOS 版本按所用 .NET、Avalonia、原生 API 及实际验收环境的交集确定，并写入 Release 和包元数据。
- Mac 正式公开包使用 Developer ID、Hardened Runtime、notarization 与 stapling，按正确次序签名嵌套 helper、原生库和主应用；窗口权限不依赖随意启用的 entitlement。
- 签名、公证需要维护者的 Apple 开发者账号与证书条件；Windows 公共分发的代码签名同样需要对应证书。尚未具备时只能准确标注内部试用状态。
- GitHub Actions 构建、测试和生成包；签名凭据通过受限 CI 配置提供，不进入仓库或日志。受信任发布事件才接触签名材料。
- 为两个平台分别验证从干净安装、前一个 Avalonia 版本升级，以及 Windows 旧 WPF 数据导入。数据迁移有版本检查和备份，不直接覆盖不可兼容的设置。
- 先实现版本检查与明确的下载/升级入口，再实现用户确认后的包下载和安装；首版不做后台静默替换。稳定与预览通道分开，不依赖开发分支名选择版本。
- 发布元数据包含版本、平台、CPU、最低系统、下载地址和校验信息。SHA256 检查传输完整性；真实性还需可信发布来源和签名验证，不能仅凭哈希认定包可信。
- Windows 安装器退出运行实例后升级；Mac 使用经过验证的应用替换和重新启动流程，不能在运行过程中覆盖内部文件。取消、断网、下载损坏、版本降级和安装失败保留可用旧版。
- 保持 Bundle ID、签名身份及数据位置稳定，并实际检查 Mac 更新后权限状态。Release 提供 Setup/DMG、SHA256、版本说明、支持矩阵与故障排查。

验收：未装 SDK/运行时的普通用户可以安装，两端升级保留设置、凭据和记录；坏包无法安装，失败后旧版仍可启动，更新后划词可用。

## 验证条件与当前限制

- 本机 Windows 可以验证 Windows 原生输入、PDF 兼容、真实 UI 和 Setup，也可完成共享协议与可控响应测试。
- GitHub macOS runner 用于编译 Swift/C#、核心测试、打包与允许的原生检查。托管 runner 的 GUI 与 TCC 授权条件不能替代用户桌面验收。
- Mac 首次授权、授权撤销、全局鼠标、其他应用选区、Spaces、复制恢复和升级后权限，需要可交互 Mac 或具备对应条件的自托管环境。
- 维护者此前暂缓 Mac 验证；本路线图列出恢复后的工作与门槛，本次没有启动 Mac 实现或改变已暂缓的验证安排。
- Apple Silicon 与 Intel 的构建、运行和应用兼容性分别记录。只验证一种架构时，另一种保留为待验收。

## 跨平台产品完成定义

只有同时满足以下条件，才将下载入口和 README 标记为 Windows/macOS 均可用：

1. Windows 与已声明支持的 Mac 架构都能安装、启动、授权、后台运行和退出，不依赖用户预装开发环境。
2. 支持矩阵内的外部划词可通过直接读取或安全复制回退完成，失败可理解、可回退，正常复制不受破坏。
3. 两端使用同一翻译与设置机制，浮窗、解释/问答、修正、记录等已声明能力没有被悄然省略。
4. 请求可取消，旧结果不覆盖新选区；原生 helper、网络和存储错误不导致主进程崩溃。
5. 首装、升级、权限、睡眠唤醒和长期运行有实际环境记录；构建成功没有被当作产品验收完成。
6. 安装包附带必要许可证，Release 明确版本、架构、支持范围和更新方式，用户数据在升级与默认卸载中被保留。
