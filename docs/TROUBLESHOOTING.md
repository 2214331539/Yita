# Yita 兼容性排查

## 连接测试成功，但划词没有浮窗

“测试连接”会使用设置窗口当前填写的参数发送一次 `hello` 翻译并等待首段文字，但不会保存这些参数。测试成功后仍需点击“保存”，并确认托盘菜单“启用划词翻译”已勾选。

先在普通网页按住鼠标左键拖选一句英文，松开后等待；当前自动触发以鼠标拖选为准。再手动 Ctrl+C，使用托盘“翻译剪贴板”或 Ctrl+Shift+T。若快捷键被其他程序占用，以托盘菜单测试为准。

- 剪贴板翻译正常、拖选无反应：检查取词和鼠标捕获。可以在设置中开启“兼容性剪贴板回退”并保存后重试；这会在安全检查通过时模拟复制，并尝试恢复原剪贴板内容。
- 托盘剪贴板翻译也无结果：继续检查已保存配置、提示错误与浮窗状态，不能仅凭现象认定是网络问题。
- 点击托盘“修复划词捕获”后再拖选，仍无结果时，保持 Yita 运行，使用“复制性能诊断”并提交文本。报告可以区分没有收到请求、读取为空、请求失败及浮窗状态；不包含正文和凭据。

出现过进程退出时，也可运行 `scripts/Collect-Yita-Diagnostics.cmd`，在桌面生成诊断 ZIP。脚本仅收集版本、经过字段过滤的健康日志和近期 Yita 崩溃事件，不读取完整设置或凭据，不更改防火墙，不自动上传。纯取词失败优先提供托盘性能诊断，因为内存中的请求统计不会保存到健康日志。

## WPS PDF 没有浮窗

0.8.0 的取词顺序是 UI Automation → Win32 文本控件 → 可选 WM_COPY。自绘 PDF 画布可能不公开 TextPattern，也不响应 WM_COPY；此时可以手动 Ctrl+C，但自动取词仍返回空。浏览器或 Markdown 可用，并不能证明同一读取路径适用于 WPS。

0.8.1 新增有前台焦点检查的 Ctrl+C 回退。默认启用“WPS PDF 兼容取词”，仅针对 wpspdf/kpdf，或标题包含 .pdf 的 wps 窗口。其他阅读器以及没有 .pdf 标识的 WPS 窗口，可按需开启“兼容性剪贴板回退”。程序先尝试不使用剪贴板的读取；失败后才启动复制事务。复制期间会临时改变剪贴板，尽量恢复原内容；若用户或其他进程已产生新的剪贴板内容则放弃恢复。

自动复制不会提升程序权限。高权限阅读器、禁止复制的 PDF、没有文本层的扫描件，以及不接受模拟复制的程序仍可能不工作。此时先自己 Ctrl+C，再按 Ctrl+Shift+T。后者只翻译已有剪贴板内容。

本次验证覆盖回退范围和已有读取链的自动化测试，尚未完成真实 WPS PDF 的端到端回归。复测时请确认设置中的 WPS 专用兼容开关启用，松开鼠标后稍等，检查普通 Ctrl+C 是否仍正常。

0.8.2 针对 WPS 将无障碍读取预算从 800 ms 缩短至 120 ms，并直接尝试复制快捷键，跳过 WM_COPY 的等待。仅当第一次未改变剪贴板时有限重试一次；已有内容变化时不会重复复制。程序改为查询前台 GUI 线程的焦点，兼容 WPS 外框与 PDF 渲染子进程；剪贴板同一所有者分批写入文本或在读取时延迟生成文本，不再立即判为失败。

`runtime-health.log` 中 `WpsCopySucceeded` / `WpsCopyEmpty` 的 `code` 是复制事务耗时（毫秒），不含选中文字，也不代表全部翻译耗时。托盘“复制性能诊断”可以区分“读取选区”和“首段译文”的耗时；如果取词快但译文晚，需检查 API 首段响应。实际 WPS 成功率和整体速度需要在真实文档上验收，不能用代码中的超时上限代替实测。

## 划词时闪退

0.8.3 将外部 UI Automation 调用移至独立进程，覆盖 `TextPatternRange.GetText` 等原生调用引起进程终止的风险。父进程通过管道获取结果；子进程异常退出、协议失败或读取超时后，当前目标的 UIA 路径暂时跳过 60 秒，并继续尝试原生取词与已有的前台复制回退。普通“无选区”返回不会强制开启通用剪贴板回退。复制仍须通过前台、焦点、按键和目标进程检查，尽可能恢复原剪贴板。

健康日志新增 `SelectionWorkerFailed`，`code` 为可获取的子进程退出码，否则为 -1；超时或取消也可能记录该事件，不能把每条都当作原生崩溃。托盘诊断新增独立进程的成功、空选区、失败计数。子进程无窗口、不加载配置或凭据，不争抢主程序单实例；父进程退出后它也会退出。

用户提供的截图描述了 `GetText` 导致运行时终止，但不是原始堆栈。本次本地故障注入验证子进程退出和挂起后的恢复；尚未在朋友电脑上复现同一原生崩溃。进程隔离的依据见 [Microsoft 关于 AccessViolationException 的说明](https://learn.microsoft.com/en-us/dotnet/api/system.accessviolationexception)：损坏进程状态的异常不能依赖普通异常捕获来恢复。

本机排查时没有找到匹配用户反馈的 Windows Application Error / .NET Runtime 崩溃事件；原健康日志中最后一次退出为 ShutdownRequested / AppExited，退出码为 0。它只能说明该次退出走了正常流程，不能排除其他设备或时间发生闪退。

代码中发现流式文字的 DispatcherTimer 帧在请求任务的异常捕获范围之外。0.8.1 在该边界拦截可恢复的 WPF/COM 呈现异常，停止定时器、记录 PopupRenderFailed 并关闭受影响浮窗；其他窗口与应用继续运行。关闭窗口后排队的定位和选区按钮更新会被跳过。这是针对风险点的加固，尚无证据证明它对应所有已报告的闪退；不会把所有全局异常一律标为已处理。

若仍出现问题，请提供：

- Yita 版本、发生时间、目标软件与版本、当时是拖选还是切换浮窗。
- `%LOCALAPPDATA%\Yita\runtime-health.log` 与同目录存在时的 `.previous` 文件。
- Windows 事件查看器“Windows 日志 → 应用程序”中同一时刻 Yita.exe 的 Application Error / .NET Runtime 事件。

健康日志仅记录事件、异常类型、HRESULT 和最多若干个应用方法名；不写入异常消息、源文件路径、文档正文、译文或 API Key。没有异常记录而进程消失时，需要结合系统事件定位原生崩溃或外部终止。

## 浮窗位置

按住顶部拖动区或工具栏空白处移动，正文仍支持选词复制。0.8.3 以每次鼠标拖选区域的左下角为基准（起止点的最小 X、最大 Y），不依赖拖选方向，也不是上次的桌面坐标。保存窗口左上角相对此基准的 DIP 偏移；下次按新选区和屏幕 DPI 换算，并限制在屏幕工作区。贴边限制不会覆盖保存的偏移。移动后，当前流式结果不会再次拉回或自动撑大窗口，可自行拉伸；换到新锚点解除本次移动锁定，固定窗口保持原位。

数据位于 `%LOCALAPPDATA%\Yita\popup-placement.json`。删除这个文件并重启可恢复默认定位。不是固定的桌面绝对坐标；卸载会保留该偏好。
